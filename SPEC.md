## 1. Stack and runtime
- **Language:** Python, managed with `uv`.
- **Media manager:** FastAPI backend, Jinja2 templates, Bootstrap 5, HTMX for live updates, Alpine.js for small interactions, Font Awesome Free icons, wavesurfer.js (regions plugin) for the waveform editor. No JavaScript build step.
- **Versioning:** one project version (`mam/__init__.py`, semver), shown by `mam --version` and in the portal footer. CHANGELOG.md lists changes per component. Versioning started on 2026-11-01, when the media manager and Renamer were approved (1.0.0).
- **CLI:** a single entry point `mam`:
  - `mam serve`: start the media manager
  - `mam <tool> [--dry-run] <path>`: run one tool on a file or folder
  - `mam scan`: index the archive
  - `mam doctor`: check ffmpeg/ffprobe, the transcription backend and models, `.env`, and whether Baserow can be reached
- **Install:** `uv sync`. External binaries (ffmpeg, ffprobe, whisper-cli) come from Homebrew on macOS and winget on Windows.
- **Transcription:**
  - macOS (Apple Silicon): `mlx-whisper` with the large-v3-turbo model (`mlx-community/whisper-large-v3-turbo`, installed by `uv sync`)
  - Windows: whisper.cpp `whisper-cli` with the GGML large-v3-turbo model
  - Both backends sit behind one transcriber interface. Each run records engine, version, model hash, backend and any fallback (see ARCHITECTURE.md).
  - **Robust transcription (decided 2026-11-21, after a 75 minute class stalled mlx-whisper for 17+ minutes):** the recording is transcribed in chunks of about 5 minutes (`TRANSCRIBE_CHUNK_S`), each cut at the quietest spot, by mlx-whisper in a watched child process that loads the audio and model once. A chunk that takes longer than `TRANSCRIBE_CHUNK_TIMEOUT_S` (240 s; a normal chunk takes about 10 s) is killed and retried in a fresh process with Whisper's temperature fallback (compression-ratio, log-probability and no-speech checks); if that fails too, whisper.cpp transcribes that chunk when it is set up (`WHISPER_CLI`, `WHISPER_CPP_MODEL`); otherwise the job fails with the chunk named, and can be retried. Each chunk is logged with its time. A stretch of 20 to 90 s without any text in the first 15 minutes (Whisper skipped it as "no speech", seen on the Oslo class where the reading of the translation was missing) is decoded again with the no-speech and log-probability checks switched off. Repetition loops ("the smile, the smile, ...") are collapsed to one copy, and every retry, fallback and collapse is recorded with the transcript. The class-discoverer treats a transcript with many repeated or invented lines (more than 25%) as unreliable: "no verse heard" then goes to review instead of Done.
- **Local database:** SQLite on the local disk, never on the NAS share. Export and import use the SQLite file plus a JSON/CSV dump command.
- **LLM:** a pluggable provider interface. The default is the Claude API (latest model, key in `.env`); a local model is optional. Results are cached by (input hash, prompt version) so re-runs are not billed again.
  - The Renamer is deterministic (date parsing, regexes, lookups). It uses the LLM only as a fallback for unusual or foreign-language folder and file names.
- **Speaker separation:** lightweight speaker embeddings (for example SpeechBrain ECAPA) are compared against a KKS voice profile built from the sample files (see section 10). A segment that is "not KKS" is an audience candidate.
- **Vedabase:** verse pages are fetched on demand and cached in the local DB indefinitely. Requests are at least 10 seconds apart (the crawl delay in vedabase.io's robots.txt, checked 2026-11-21) and send a clear User-Agent. The delay is hidden by the transcription: the class-discoverer fetches the filename's verse pages while the recording is transcribed. A range has no page of its own (`/sb/9/20/20-27/` is a 404), so only the first and the last verse of a range are fetched.
- **Concurrency:** a job queue persisted in SQLite, with a worker pool per resource. Defaults: 1 ML worker (transcription, embeddings), ffmpeg/CPU workers (one per core, keeping two free, at most 8; the Kirtan splitter runs here, its analysis in separate processes), and I/O workers for copies and Baserow. All sizes are configurable in `.env`. The queue survives restarts, so the Renamer can process hundreds of files while ML work runs one file at a time.
- **Users:** one operator on localhost. The server binds to 127.0.0.1 with no authentication. The operator name from config is recorded on every approval.

## 2. Files, identity and storage
- **Originals are read-only by default.** Tools never rename, move, modify or delete an original; every tool works on copies. **Two Renamer options (Settings page, decided 2026-11-21) change this on purpose, both off or empty by default**, so that high-confidence files can be processed automatically in the 15 TB archive:
  - *Move files instead of copying*: the Renamer moves the original into processed-files. See the Renamer section for how a move is kept safe.
  - *Add postfix to processed filenames*: after a copy, the original left behind is renamed with the postfix (`name_processed.mp3`) to show it is done.
  No tool other than the Renamer ever touches an original, and nothing else about originals changes (file contents are never modified).
- **NAS access:** through a mounted share (root path in `.env`). Files are read directly from the mount, temporary and intermediate files go to local disk, and final outputs are written to the processed-files root (path in `.env`).
- **Identity:**
  - At scan time each file gets a quick fingerprint: size, mtime, and an xxhash of the first, middle and last 4 MB.
  - A full SHA-256 is computed lazily, when the file is processed or when two fingerprints collide.
  - Derived files (kirtan/class split, trimmed, optimized) get their own IDs, linked to their source with `parent_id`.
- **Scope:** only audio and video extensions are scanned. Everything else (photos, zips, ebooks, design files) is ignored.
- **Copying into processed-files:**
  - The Renamer copies the file to `processed/<category-folder>/` immediately, and later tools write new versions there.
  - The category folder is found by matching the WHAT against the Baserow `category_terms_folder` table.
  - With no WHAT the file goes to `unprocessed-files/` (a sibling of `processed-files/`, not inside it). It moves to its category folder once a later tool or a reviewer finds the WHAT; the history is kept.
- **Identical copies (decided 2026-11-21):** byte-identical copies of a file (found by a scan, recorded as aliases) go to their own folder `identical-files/` in the repository root; with `processed-files/` and `unprocessed-files/` these are three sibling folders (paths `MEDIA_IDENTICAL_FILES_PATH`, `MEDIA_UNPROCESSED_FILES_PATH`; no nesting). They are handled when the Renamer runs on the file they duplicate, with the same Renamer option as the file itself: copied, or moved (verified copy, original removed only after the check) when *Move files instead of copying* is on. They keep their own filename (`-2`, `-3` on a clash), never get the postfix, are handled once, and each move or copy is a `file_event`. Dry runs say "would copy/move". Reject and Exclude put moved copies back; the Settings reset refuses while moved copies exist.
- **Original folders are kept (decided 2026-11-21):** in `unprocessed-files/` and `identical-files/` a copy keeps the folders its original sat in, below its import root (`Sample files/2012/Radhadesh Jan 2012/x.mp3` gives `unprocessed-files/2012/Radhadesh Jan 2012/`), because those folder names are clues for whoever sorts the files later. A file straight in the import root gets no subfolder; a file outside every import root keeps its parent folder's name. `processed-files/` stays flat per category. When a later tool or a reviewer finds the WHAT, the file moves to its category folder.
- **Name clashes:**
  - Same final name, different content: append `-2`, `-3` before the extension and flag the file for review.
  - Same name and same size (a duplicate): copy it with a `_duplicate` suffix, as the file-organizer spec requires.
- **After a kirtan/class split:** the combined processed copy is discarded and the original stays on the NAS. The combined file's Baserow row becomes the class row, and the kirtan gets a new row.
- **Ingest:** four ways to add files:
  - browse and import NAS folders (the Import page lists the subfolders first, then the media files directly in the browsed folder with their size; other file types are not listed). Each folder and file has a checkbox (plus select all); **Import** (left) imports only the ticked ones (a ticked folder with all its subfolders, a ticked file alone), and **Import all** (right) imports the whole browsed folder with its subfolders). The top bar has an **Add media** button (on every page) that opens the Import page
  - a full archive scan (index only, no processing)
  - drag-and-drop upload into an inbox folder
  - a watched inbox folder, whose new files are registered automatically

## 3. Filename rules
These clarify docs/references/filenaming-convention.md.
- WHO is always `KKS`.
- A file is always renamed with whatever W's are known. For example, a file with only a date becomes `YYYY-MM-DD_KKS.mp3`.
- Date parts may use the `YYYY`, `MM` and `DD` placeholders. WHO, WHAT and WHERE never use placeholders; a missing segment is left out.
- WHERE takes one of three forms:
  - `Place-cc`: place in Title-case, ccTLD in lowercase
  - `cc`: country only
  - omitted, when nothing is known
- Recordings from the same day are told apart by their WHAT. Only a full collision gets a `-2` suffix.
- WHAT is the verse plus the short title from the content-discoverer, for example `SB-9-20-20-Dont-waste-time`. The content-discoverer title replaces the class-discoverer title.
- The whole filename stays between 25 and 128 characters.

## 4. Processing pipeline and tools
Pipeline order: **renamer → kirtan-splitter → class-discoverer → content-discoverer → class-trimmer**.

- Each tool can run on its own (one file or a batch) or as part of a pipeline coordinated by the media manager.
- In a batch, a flagged file pauses on its own while the other files continue. After approval it resumes automatically at the next step, and the approval message says which tool was queued (with the live spinner, decided 2026-11-07).
- Kirtan-only outputs are `Skipped` for steps 3 to 5.
- **Video:** the pipeline is audio-only. Video files are renamed and copied but never edited.
  - **After the Kirtan splitter (decided 2026-11-05):** the audio rows (the class, and the kirtan when there is one) continue through the pipeline as audio. The video row is finished after the split and its video file stays untouched. What the later tools find for the class audio (verse, title, themes, language) is also written to the video's own Baserow row, under the same rules as any other write (empty fields only; a person's values are never overwritten), so the video gets the same name details as its class audio. The video's filename follows the Renamer's rules with that evidence.
- **Cutting:** splits and trims use stream copy in the original codec (no re-encode), because most sources are already lossy. Gain changes need a re-encode, written at the source codec, bitrate, sample rate and channel count.
- **Loudness method:** loudness is measured with ffmpeg `ebur128`. When the peaks allow it, the gain is a pure linear change. When they don't, the gain is followed by a peak limiter running at 4× the sample rate (so inter-sample peaks are caught), with one corrective pass if limiting cost loudness. This was chosen over a two-pass `loudnorm` because it is about 7× faster with the same result. Files that needed the limiter are marked `dynamic` so they can be flagged.

### Renamer
- **Evidence order:** filename > parent folder names > ID3/tags (medium to high confidence) > Baserow media table > travel schedule. Each W is resolved on its own.
- **Travel schedule:** evidence only, never a source on its own: it says where KKS possibly was on a date. It never gives a place its country and is never written by the portal.
  - A date inside the exact `[start_date, end_date]` range supports the place, and the reverse.
  - It fills WHERE only when the filename has no place.
  - It never overrides the filename or the folder.
- **The Renamer flags a file for review when:**
  - the filename is non-descriptive
  - the date format cannot be determined, even with the travel schedule and the media table
  - a new place or country is needed. The flag reads "New place 'X' is not in Baserow. Add it as a place_location option in Baserow, or correct it" (never the travel schedule, which is not written); saving the file with that place and its country adds it to `place_country`.
- **The Renamer also flags a file when:**
  - the filename names another speaker (e.g. `SNS`, `BVS`) and not KKS, since WHO is always KKS
  - the country code contradicts a place that has no single country in Baserow and cannot be corrected safely. A code that contradicts a place Baserow knows with exactly one country (`Oslo_fi`, Oslo is in Norway) is corrected to the place's country without a review and noted in the Baserow `notes` (decided 2026-11-22)
  - a different file already has the final name (it is saved with `-2`)
- **Missing WHAT:** the file goes to `unprocessed-files/`, and later tools may fill in the WHAT.
- **Dates:** European day-month-year is the default reading; other orders need supporting evidence. Dates in the ID3 title or date tag are taken as correct unless other evidence conflicts (a conflict with the folder name is flagged). See docs/references/filenaming-convention.md.
- **More evidence used:**
  - sibling files in the same folder decide ambiguous dates (`08-04-10` among April 2008 files is 2008-04-10) and give the place of files recorded the same day
  - when nothing else gives the country, the places named by the other files in the folder do, if they are all in one country (`KKS DUBEN 2008 MP3/02 KKS. SB. 3.1.20.mp3` gets `cz` because `03 BRNO LEKCE…` is in the same folder); the city stays open, and places in two countries give no country
  - the travel schedule only suggests places in the country the filename names; every stay on the date is shown as evidence, and on a travel day (leaving one place, arriving in another) the place is left open
  - a new place flag suggests the closest known place (`Fruska-Goranga`: did you mean `Fruska-Gora`?)
  - place spellings (`Praha`, `Koln`, `Rdesh`) are the `place_country.Aliases` column in Baserow (decided 2026-11-21); the words that mean a language (`GER`, `deutsch`) are the `language_terms` table, the country words (`Holland`, `UAE`, `Cesko`) the `country_terms` table, and a place that is no real location or has no country is a `not_place` or `no_country` checkbox on its `place_country` row (all decided 2026-11-21). Only speaker acronyms and noise words are still in `mam/tools/renamer/aliases.yaml` (see docs/references/filenaming-convention.md)
- **Summercamp:** a filename (or a folder name) with `summercamp` in it (`Serbia-Summercamp`, `Swiss summercamp`, `Summer-camp`) gets the `Summercamp` category, unless the filename has a book and verse; then the book's category (`SB-1-2-3` gives Srimad-bhagavatam). Only an existing Baserow category option is used.
- **WHAT from the folder (decided 2026-11-21):** when the filename gives no WHAT (a recorder name such as `R09_0008`, `ZOOM0001`) and the category comes from a parent folder (`Vyasa puja 2015` matches `Vyasa-puja` in `category_terms_folder`), the category name is the WHAT: `2015-MM-DD_KKS_Vyasa-puja.mp3`. Files of the same folder that end up with the same name get `-2`, `-3` (the clash rule). Not used for the scripture categories (Bhagavad-gita, Srimad-bhagavatam, Caitanya-caritamrta, CC-*-lila: a book needs a verse) or `Unknown`/`Various`. The file is then no longer flagged as non-descriptive; the evidence list shows the WHAT as coming from the folder.
- **Category words come from `category_terms_folder` (decided 2026-11-21):** the table's `filename_terms` match both filenames AND parent folder names, for the category and (for folders) the WHAT. The words dropped next to a verse (`SB 3.1.20 class`) are the terms of the `Class` row too (`Lekce, Lecture, Class, Lezing, Vortrag, predavanje, lecture-class`). A word that should mean a category (for example `Lekce`, `Lecture`, `Class`) is added as a term on a row of that table, not hardcoded in the Renamer. The Renamer has no category word list of its own any more (the `categories` seed list was removed from `aliases.yaml`, 2026-11-21): every category word comes from the table.
- **Class (decided 2026-11-21):** the table has a `Class` category (terms `Lekce, Lecture, Class, Lezing`, folder `class`). A file in a folder like that, whose name gives no other clue, is named `YYYY-MM-DD_KKS_Class.mp3` and goes to the `class` folder in processed-files. The class-discoverer later finds the real type and the file moves to its own category folder. A verse in the filename wins (`SB 3.1.25` is Srimad-bhagavatam, not Class).
- **Category type (decided 2026-11-24):** the `category_terms_folder` column `type` (`class` or `kirtan`) tells the tools which categories are kirtans; the Renamer has no kirtan category list of its own. The Renamer may still file a recording in a `class` category before the splitter has listened (it works on names only and must stay standalone); the splitter then corrects it, and a combination name (`SB-1-19-31-with-radha-madhava`) keeps its scripture category until the split.
- **Bhajans are always Kirtan (decided 2026-11-23):** a name with a word of the `Kirtan` category (`Bhajans`, `Bhajanas3`; a source index glued to the word is ignored) gets the category Kirtan, even when an event category such as Radhastami comes first in the name (`Radhastami-Bhajanas`): only classes go in the Radhastami and Nrsimha-caturdasi folders. Not for a combination: a scripture first (`SB-1-19-31-Bhajans`) or the word after `with`, `and` or `plus`. Spellings that are not in the table (`Bahjanas`) need a term on the `Kirtan` row of `category_terms_folder`. `Nrsimha-pranama` is a kirtan category of its own (a row in `category_terms_folder`).
- **Rule-based:** the Renamer does not call the LLM; unusual names are flagged instead.
- **Confirmed values:** what a person saves on the file page or approves in a review is stored as *confirmed*. A later Renamer run keeps confirmed values and only fills what is still empty (or completes a date with placeholders). Other tools pass what they discover as evidence (e.g. the class-discoverer's verse); when it contradicts a confirmed value the file is flagged for review instead of being overwritten.
- **Renamer options (Settings page, block "Renamer"; decided 2026-11-21).** Stored in the local DB (`app_setting`), read by every run, so a change applies to the next run.
  - **Move files instead of copying** (off by default). The original is moved to processed-files instead of copied. Dry runs say "Would move". A move is never lossy: on one volume it is a single rename; across volumes (NAS to local disk) the file is copied, read back and compared (size and SHA-256), and only then is the original removed. If the check fails, the destination is not created and the original stays. If the original cannot be removed (read-only share, permissions) both files stay and the run says so. A name that is taken is never overwritten (`-2`, `_duplicate` as for a copy). The record keeps the original path for name evidence and marks `original_moved`; because the processed file is then the only copy, **Reject** and **Exclude** put it back where it was imported (verified, never trashed; refused with a message if that place is taken), **Delete** still goes to the Trash but says it was the only copy, and the Settings **Reset** refuses to delete processed copies while such files exist. The postfix is not used when moving, because no original is left behind.
  - **Add postfix to processed filenames** (empty by default, so no postfix; example `_processed`). Applies to a copy, and only to the *original left behind*, which is renamed `name<postfix>.ext` once the copy is complete (`2008-01-04.mp3` becomes `2008-01-04_processed.mp3`). The new copy keeps its clean name. It is added once (a name that already ends with it is left alone), never overwrites (`-2`), and a refused rename (read-only share) is only a warning; the copy is kept. Reject and Exclude give the original its own name back. Letters, digits, `_` and `-` only, at most 30 characters. A re-run of the Renamer reads the ID3 tags from the renamed file and keeps using the import path for the name evidence. Rescanning a folder finds the renamed original as a byte-identical alias, not a new file.
  - Every move and every rename of an original is recorded as a `file_event` (`move`, `mark_original`, `restore`, `unmark_original`).
- **Every run is copied:** a flagged file is still copied and renamed (into its category folder or `unprocessed-files/`), so the review edits a real copy. Running the Renamer again on a processed file moves that copy; it never makes a second one.
- **Dry run:** shows the proposed name in the file list without copying files, changing the status or writing to Baserow. It never opens a review; the file page says so and offers to run the Renamer for real.

### Kirtan-splitter
- **No transcription.** The splitter decides from the audio alone, with local processing. Transcription belongs to the class-discoverer. **Common phrases are ignored for now** (they need a transcript, which does not exist when the splitter runs); the instruction returns when a transcript is available.
- **Video first:** extracts the audio as mp3 in its original quality (an mp3 stream is copied, other codecs are encoded once at their own bitrate), with a name that matches the video. The video copy stays as it is; the class audio becomes its own row, a child of the video.
- **Speed** (measured 2026-11-04 on a 10-core Apple Silicon Mac, 62 to 73 minute recordings): the audio is decoded once for the speech model, the loudness/treble measure and the silences (it was three times; identical results), which takes a file from about 36 s to about 26 s (about 165 times real time). Files run in parallel in separate processes on the CPU pool (up to 8 at once): 8 clips in parallel gave 5.3 times the throughput of one at a time, threads only 2.6 times. Setting `ANALYSIS_IN_PROCESSES=false` runs the analysis in the worker threads instead. **Early stop** (decided 2026-11-04): the decision looks only at the first 300 s of the class (the speech-versus-kirtan contrast), so the decode ends once the class's first speech run, after a kirtan of at least 90 s, has ended or has lasted 330 s, and the speech so far adds up to the 3 minutes of a class (`ANALYSIS_EARLY_STOP=false` turns it off). The cut and the sure flag are the same as with the whole file (tested on synthetic profiles and compared on the real samples); a recording where the class is not found, or the result is not sure, is analysed in full again, so every review has the whole timeline. A kirtan of barely 90 s plus a lead-in silence may be analysed in full, because the lead-in is not known yet and the check counts the music from 60 s. Measured 2026-11-04 on the five trimming samples and the Amsterdam file: the same mode, sure flag, cut and class start on all six; five stopped early (analysed 512 s to 2176 s, taking 2.9 to 11.7 s instead of 21.9 to 32.4 s); the Amsterdam file (music until 4288 s) is analysed in full. The stored contrast differs slightly on three files (for example 0.447 against 0.497), because it is now measured over the first 300 s of the class.
- **Needs the Renamer first:** a real run cuts the renamed copy in processed-files. A dry run (`mam kirtan-split <file>`) may read any file and writes nothing; it prints a timeline of what was heard (`m` music, `s` speech, `.` silence, one character per 10 s).
- **Boundary detection** (`mam/tools/kirtan_splitter/`): every second of the recording gets the probability that someone is speaking, from the Silero voice-activity model (MIT licence, a 2.3 MB ONNX file in the repository, run locally with onnxruntime on macOS and Windows; nothing is downloaded). Singing with instruments scores near 0 and a class well above 0.10 (on the five trimming samples: kirtan 0.00 to 0.01, class 0.41 to 0.65 on average). The score is averaged over 9 s.
  - The class starts at the first run of at least 20 s of speech that has a **kirtan before it: at least 90 s of music, and at least 70% of the sounding seconds before the run are music** (decided 2026-11-07). Scattered quiet seconds in a long class do not add up to a kirtan: three Stockholm classes (March 2015) were cut after 40 to 55 minutes of "kirtan" that was 98% speech. The first second of the run that really speaks is the first speech.
  - **An opening mantra is part of the class, not a kirtan** (editing standard, point 1; decided 2026-11-07). A class often opens with a sung mantra of 30 s to 3 minutes. Sung without instruments it scores as speech on the voice model (0.3 to 0.9 on the Stockholm files), so the class simply starts at second 0; a shorter spell of music before the speech (30 to 40 s on two Stockholm classes) is the same mantra. Neither is split off. A real kirtan has instruments and treble and is at least 90 s of mostly music (the smallest golden example, SB 3.6.6, is 147 s).
  - **The kirtan ends where the music stops, not where the speech starts.** On the five samples the documented kirtan end is 20 to 70 s before the first speech: a sung prayer, applause or a quiet room scores 0 on the voice model, like the kirtan itself. The splitter therefore measures, per second, the loudness (RMS dBFS) and the share of the energy above 2 kHz (cymbals, kartals). A second counts as music while it is within 20 dB of the kirtan's own loud level (the 80th percentile) and, when the kirtan has treble (high-band share of at least 0.03), keeps at least 40% of the kirtan's median high-band share. Each second is judged by the majority of 5 s around it. The kirtan ends at the first stop of at least 4 s that comes after at least 90 s of music, unless music of 45 s or more returns before the first speech (then it was only a pause). With no such stop, the cut is at the first speech and the score is lower (base 0.20 instead of 0.35), so the file goes to review.
  - On the five samples the cut lands 0.1 to 0.4 s from the documented kirtan end on three and about 2 s early on two (2008-01-04-2 and SB 3.6.6), where the sound fades out over several seconds. The cut is always at or before the end of the fade, so no music is lost from the class. The golden test therefore allows 2.5 s for the splitter, not the 1.5 s of section 9 (2026-11-01).
  - The cut is moved into a silence (ffmpeg `silencedetect`, -40 dB, 0.8 s) within 3 s, and silence at the very start is trimmed. None of the five samples has such a silence at the cut yet, so all five score 0.8; they are cut by the rule under Automation below, not by a score.
  - Why not simpler audio measures: pauses, zero-crossing rate and syllable rhythm were tried first and found the right cut in only one of the five samples (2026-11-01).
- **No split:** music throughout is a kirtan recording; speech with no kirtan of at least 90 s before it is a class. Both are `Skipped` when sure, and go to review when not. Speech after the kirtan counts as a class only when at least 3 minutes (`MIN_CLASS_S`) of speech follow the music; less is a **spoken ending** (closing words, an announcement) and the recording is still a kirtan recording, `Skipped` when sure. The same holds at the start: less than 3 minutes of speech in a recording of music (a 90 s announcement before 43 minutes of bhajans) is no class, so the recording is a kirtan recording. A mostly-music recording (70% or more) with a talk in the middle and at least 5 minutes of music again after it is a kirtan programme with talks: it is a kirtan recording, `Skipped` when the music after the last talk lasts 10 minutes or more (sure), otherwise proposed and sent to review (decided 2026-11-07, after Stockholm 2015-03-08). Example: the Home program Amsterdam recording of February 2015 is 71.5 minutes of kirtan followed by 40 s of talk at the very end; it is not split (2026-11-04). The splitter applies no fade-out: the editing standard allows no fades, and any trimming of a kirtan recording belongs to a later trimming tool, not the splitter (decided 2026-11-04).
- **Cutting:** by stream copy, one cut at the end of the kirtan (the stretch between the kirtan and the first speech stays at the start of the class, for the class-trimmer). The kirtan keeps the recording's date and place and takes the mantra as its WHAT. The mantra comes from the class's WHAT, as SPECS.md says: SB or BG gives `Jaya-radha-madhava`, CC gives `Jaya-Jaya-Sri-Caitanya`; anything else is named `Kirtan` and the reviewer can pick another type (including `Nrsimha-pranama`). It goes to the folder of that WHAT. The class keeps the combined copy's name, place and row (the combined copy is replaced by the class; the original on the NAS is never touched). The source extension is kept (`.wma` stays `.wma`).
- **Names are built by the splitter**, from the Renamer's saved proposal, because the derived kirtan has no original path for the Renamer to read. The kirtan has its own local record (`derivation = kirtan`, `parent_id` = the recording, status `Processing complete`) and a new Baserow media row written with the Renamer's switch rules; the class keeps its row.
- **Combination phrase dropped from the class name (decided 2026-11-22):** a source name such as `S.B. 1.19.31(with Radha Madhava)` gives the WHAT `SB-1-19-31-with-radha-madhava`, which says the recording is a combination. Once it is split the class is not, so after the split the splitter queues the Renamer with the WHAT without the phrase (`with`, `and` or `plus` followed by a term of a kirtan category in `category_terms_folder`: Kirtan, Jaya-Radha-Madhava, and Jaya-Jaya-Sri-Caitanya or Nrsimha-pranama once those rows exist; `phrases.without_combination`): the class becomes `2011-08-20_KKS_SB-1-19-31_Oslo-no.wma`. Before the split the combined copy keeps the phrase. A WHAT a person has confirmed is not changed: the Renamer flags the conflict instead.
- **Kirtan recordings go in the Kirtan folder (decided 2026-11-23):** a recording that is singing throughout (sure, or approved by a reviewer) is marked `recording_kind = kirtan` and the Renamer is queued with `keep_status`, so the file keeps its splitter status. The Renamer then sets the category `Kirtan` and files the copy there, whatever the filename says: `Radhastami-Bhajanas` would match the category Radhastami, but only classes go in Radhastami and Nrsimha-caturdasi. A WHAT that is itself a kirtan category (`Nrsimha-pranama`, `Jaya-radha-madhava`, `Jaya-Jaya-Sri-Caitanya`) keeps its own folder. This overrides a category a person confirmed earlier; the Renamer notes it.
- **Automation:** the splitter does not use a score threshold. It is **sure**, and cuts automatically, when the music clearly stops and speech follows: the end of the music is found (see above), the kirtan is 1.5 to 35 minutes (the SB 3.6.6 sample is only 2.5 minutes), the speech after the cut is at least 0.2 above the kirtan in speech probability, and the kirtan is at least 80% music. A recording with no speech is `Skipped` as a kirtan when at least 90% of it is music; speech from the start, or after an opening of at most 90 s (an opening mantra, an announcement), with the speech mostly continuing for the rest of the recording, is `Skipped` as a class (sure); a longer opening that is not a kirtan goes to review. Everything else, and a 5% random check (`SPOT_CHECK_RATE`; the review says in plain words that nothing is wrong), writes nothing and goes to `Kirtan-splitter Review`. The review page still shows a score from 0 to 1 (0.35 for a found end of the music, or 0.20 for the fallback to the first speech; up to 0.25 for the contrast; 0.15 for a cut in a silence; up to 0.10 for how purely music the kirtan is; 0.10 for a kirtan of 3 to 35 minutes, minus 0.20 outside that; 0.05 when the class tells the mantra). It is stored with each outcome for later calibration, but it does not decide. Decided 2026-11-03: the Oslo sample was cut correctly at 704.0 s (the kirtan ends at 703.484 s, the speaker then says "Srila Prabhupada, ki jaya") but scored 0.80 to 0.85, below the 0.9 of section 10, because the music stops abruptly with no silence to reward.
- **Review (on the details page):** shows the reasons, the timeline and evidence, shows the waveform editor (below), and takes the cut as `minutes:seconds` (typed or set in the editor) and the kirtan type. Buttons: **Approve and split**, **Do not split**, **Reject result**, **Exclude file**. The cut is made only on approval. An approved cut within 1.5 s of the proposal counts as approved, otherwise as edited; both are labeled examples for the threshold. 

### Class-discoverer
Decided by Edwin on 2026-11-21. Built in `mam/tools/class_discoverer/` (the transcriber is `mam/helpers/transcriber/`, vedabase.io is `mam/helpers/vedabase/`); in the Action menu and as `mam class-discover <file>` (dry run by default).
- **Order:** whole-recording gain, then transcription, then the verse.
- **Whole-recording gain:** runs the audio-optimizer on the processed copy (encode #1). The kirtan-splitter has already separated any kirtan, so the gain is measured on the class alone and loud singing cannot skew it. A recording that already meets -18 LUFS +/-1 LU is left alone (no needless re-encode). A result that needed the limiter is stored as `dynamic`.
- **Transcription:** the full recording, as spoken, in any language (language detected by the model). The transcript is cached in the local DB by the content hash of the audio, so a re-run and the later tools never transcribe the same content twice, and is written to `transcriptions/<category folder>/<base-name>.srt`. **Sanskrit glossary (decided 2026-11-22, `docs/references/sanskrit-glossary.json`):** Whisper writes Sanskrit names badly (`Harry Krishna`, `Bhagwad Geeta`), so each term in the glossary lists the spellings Whisper is known to produce (`variants`). After transcribing, a known variant is replaced by the glossary's spelling (whole words only; variants under five letters such as `Prem` are skipped because they are often real words), and the number of replacements is stored with the transcript (`TRANSCRIBE_GLOSSARY_FIX`, on). The terms can also be given to Whisper as its prompt (`TRANSCRIBE_GLOSSARY_PROMPT`, off until it has been compared with and without on real recordings, because a prompt can make Whisper invent text). **Only transcribe speech (Settings page, block "Class discoverer"; decided 2026-11-22; off by default, `TRANSCRIBE_SPEECH_ONLY` is the default):** the Silero voice model of the Kirtan splitter scores each chunk first; a chunk with speech in less than 2% of its seconds is not given to Whisper, and any text Whisper wrote over seconds that average below 0.05 voice probability (kirtan, silence, room noise) is dropped. The counts are stored with the transcript. A recording that already has a transcript is not transcribed again (use Reject result to run it again). Segment timestamps by default; word timestamps are off (`TRANSCRIBE_WORDS=true` turns them on) because they cost speed. **Improve the chanted verse (Settings page, block "Class discoverer"; decided 2026-11-22; off by default, `TRANSCRIBE_VERSE_PASS`; macOS mlx-whisper only):** once a verse is confirmed (announced and heard, or the filename's verse heard), the stretch where it is chanted (found by the loose Sanskrit match, 8 segments plus 2 s each side) is transcribed again with the verse's transliteration from vedabase.io, without diacritics, as Whisper's prompt, at temperature 0, and replaces the first text. Invented credits and loops are dropped. The prompt is never used before the verse is confirmed, because it could pull the text towards a wrong verse. Done once per transcript; the result is stored with its notes.
- **Verse discovery, rules first:** the transcript is searched for the speaker's announcement of the book with its numbers ("Bhagavad-gita as it is, chapter two, text fifty-one", "first canto, chapter nineteen, text thirty-one", digits such as "SB 3.6.6", and a range "text 20 to 27"). The announcement heard most often wins (the earliest on a tie). Only announcements in the first 10 minutes and before the speaker reads "Translation", "Purport" or "Synonyms" count (a verse quoted in the purport is not the class verse; seen on 2008-01-04-2, decided 2026-11-21). Canto spellings Whisper writes (`Kanto`, `Kanchu`, `3rd`) are read as the canto, and a number the speaker corrects ("chapter 9 ... no, chapter 19") is read as the later one, with the earlier reading tried on vedabase.io when the later is not confirmed (Oslo sample, 2026-11-21). An announcement without all its numbers ("It's thirty one, first canto") is not a verse. English number words are understood; other languages fall to the unconfirmed case below. The Claude API as a fallback when the rules find nothing is **not built yet**.
- **Confirmation on vedabase.io:** the verse page must exist, and either at least 30% (`CONFIRM_SHARE` in `match.py`, to be tuned on real samples) of the three-word sequences of its English translation are heard in the transcript, or the chanted Sanskrit matches (decided 2026-11-22). The Sanskrit is compared loosely, because Whisper spells it by ear (`prasantavasinam akuntamedasam` for `praśāntam āsīnam akuṇṭha-medhasaṁ`): both sides are reduced to their consonants (vowels, aspiration `h`, doubled letters and the twins `m`/`n` and `b`/`v`/`w` ignored) and the share of the verse's consonant trigrams found in the best stretch of 8 consecutive transcript segments is the *Sanskrit heard* value; at least 50% (`SANSKRIT_CONFIRM_SHARE`) confirms. On the Oslo class (SB 1.19.31) the right verse scores 92% and 1.9.31 scores 20%, and talk without chanting 19%. The first and the last verse of a range are checked.
- **Automation (no score threshold, like the splitter):** the class-discoverer is **sure** when the verse is announced and confirmed.
  - The filename has no complete verse: the Renamer is queued with the verse as evidence (`what`, `verse_tag`, `languages`) and the filename changes at once. Another verse than the filename's is never overwritten silently.
  - The filename has the same verse: nothing changes.
  - The filename has a **different** verse than the recording announces: both verses are looked up on vedabase.io and compared with the transcript. When the filename's verse is heard (confirmed) and the announced one is not, the filename is kept and the file is Done without a review (decided 2026-11-22: Whisper writes the numbers badly, here `1.9.31` for `1.19.31`). Otherwise the filename is kept and the file goes to `Class discoverer Review` with both candidates, how much of each translation was heard, and a transcript excerpt; the button for an unconfirmed verse says so.
  - The numbers of an announcement are read in the same segment and the next 20 seconds, so a spoken correction ("Huh? No ... Chapter 19") counts.
  - A verse that is announced but not confirmed goes to review.
  - No verse announced: a filename with a verse is kept; with no verse the WHAT stays as the Renamer set it and the file is Done when it has a category, and goes to review when it has no WHAT or category at all (festival, story or seminar recordings).
  - 5% of the sure naming decisions (`SPOT_CHECK_RATE`) are shown in review anyway and change nothing until approved.
- **Review (details page):** shows the verse heard (time, how often, vedabase.io, share of the translation heard, excerpt) against the filename's. Buttons: use the verse from the recording, keep the filename's verse, use a typed verse (e.g. `BG-2-51`), reject, exclude.
- **No title.** The content-discoverer finds the title and adds it to the filename when the filename has none yet (decided 2026-11-21). The class-discoverer adds no title.
- **No trimming.** Only the class-trimmer trims (decided 2026-11-21). The moment the verse is announced is stored as `class_start` with the result, for the class-trimmer.
- **Language:** the detected languages are merged (union) into the Baserow `language` field, through the Renamer's evidence. Only options that exist in Baserow are written.
- **Video:** a class audio cut from a video also gives its verse and languages to the video's own row, by queueing the Renamer for the video with the same evidence (empty fields only, a person's values are never overwritten). Renaming the derived class *audio* file itself (it has no original path for the Renamer to read) is not built yet.
- **Kirtan-only recordings** are `Skipped`. A recording the splitter found to have no kirtan (`class_only`) continues to this step.

### Content-discoverer
- 1 to 5 topics, each at most 2 words and not too general. They are written to the Baserow `themes` column as one text value separated by a comma and a space (`Krishna Prema, Kali Yuga`), the format the existing rows already use.
- A YouTube description in English, 2 to 3 paragraphs, always ending with the footer (current year).
- A short English title, which goes into the WHAT.
- All results are written to Baserow: the description to `media_description` (and `youtube_desc` set to true), per helpers/baserow/SPECS.md.

### Class-trimmer
- **Sections:** detects them per docs/references/editing-standard.md and cuts by stream copy.
- **Audio-optimizer pass:** then calls the audio-optimizer for audience-question gain and a final loudness pass (encode #2):
  - target −18 LUFS ±1 LU, ceiling −1 dBTP
  - a required gain above 12 dB always goes to review
- **Non-verse recordings** (festivals, seminars, workshops): trims only the leading and trailing ambience and the intro mantra, applies the Q&A gain and the final pass, and flags the file if the structure is unclear.
- **Automation:** cuts automatically when every boundary scores above the learned threshold (see section 10). Otherwise the file goes to `Class-trimmer Review`.

## 6. Baserow
- **Live writes:** tools write to the live Baserow database (there is no test database).
- **Safeguards:**
  - A **Baserow writes** switch in the portal's top bar (on every page; ON shows in red) decides whether runs write to Baserow. It is stored in the local DB, takes effect at once, defaults to **off**, asks for confirmation when switched on, and a reset turns it off again. While it is off, runs only log the rows they would write.
  - Every write is logged in the local DB with before and after values, so it can be undone.
- **When tools write:** the Renamer writes a file's row when its name is final: right away for an unflagged file, and after approval for a flagged one.
- **Live or logged:** runs (**Run** on one or many files, the pipeline) follow the switch. **Approving a review always writes live**, because it is an explicit human decision; the review page says so.
- **Matching an existing row:** the date alone never decides. Among the rows on the same date, a row matches only when it also agrees on the verse `tag` and/or the `title` (shared title words, ignoring stop words, places and countries), with `place_location`/`country` and category as further evidence. A different verse, place or country counts against the row; an online place (`Zoom-livestream`) is neutral, because a livestream happens somewhere. When several rows fit, the file is flagged so the reviewer picks the row; otherwise a new row is created.
- **Formats:**
  - `audio_file_location` / `video_file_location`: the path below the processed-files root, e.g. `/Srimad-bhagavatam/2011-08-28_KKS_SB-1-19-30_Oslo-no.wma`
  - `tag`: verse numbers only, as existing rows have them (`3.6.6`; CC with its lila: `Madhya 20.154`)
- **Overwrite policy:**
  - Tools only fill empty fields and never overwrite values a person entered. Differences are shown as proposals on the review page.
  - `notes` gets a dated entry appended for each tool.
  - `language` is merged (union).
- **Reference data cache:** the categories (with their colors), places, travel schedule and media index are read from Baserow and kept in memory and on disk (`~/.mam/cache/baserow_reference.json`). Pages use the cached copy at once; data older than 10 minutes is refreshed in the background, so nothing waits for Baserow. Work that files a recording (Renamer jobs and saving an edit) fetches fresh data first when the cached copy is over 60 seconds old, so a search term just added to `category_terms_folder` counts; if Baserow is unreachable it falls back to the cached copy. Saving a file with a new place and country refreshes it straight away.
- **Schema:**
  - Only existing columns and select options are used. The schema is refreshed at runtime.
- **Place and country:** the `place_country` table (one row per media `place_location` option: `place_location`, `country`, `ccTLD`) is the only source of a place's country. General places (Zoom-livestream, Home-program, Summercamp, Govindas; `no_country` in `mam/tools/renamer/aliases.yaml`) have no country: the file's own evidence decides. It was filled once with `uv run mam place-country sync`, which also gave media rows with a place but no country that place's country and unified the `Czech-republic`/`Czech-Republic` spelling. A person's save adds a missing row or fills an empty country, live; a row with another country is never changed (the file page warns at the Country field).
  - The `place_country` table also has an `Aliases` column (read ignoring case), filled by hand: other spellings of the place separated by semicolons (`ISKCON-Korsnäs-Gård` has `New-Radhakunda-Dham;NRK`). The Renamer reads them with the table and treats an alias like the place itself, so the filename gets the canonical place and its country. An alias written by hand wins over a real place of the same name and over the seed aliases (`Fruska-Gora` listed on `Summercamp` makes `Fruska-Gora` mean `Summercamp`); when two rows list the same alias the first row keeps it. An alias can point at a place that `not_places` hides by its own name (`Summercamp`: the bare word is not a place, its listed aliases are). The portal never writes `Aliases`.
  - The `users` and `media_review_tasks` tables are ignored.

## 7. File statuses
- `Not processed`
- `Queued`: waiting in the job queue (no tool name, decided 2026-11-23)
- `Processing`: a tool is working on it (no tool name, decided 2026-11-23)
- `<Tool> Done`: finished this step, waiting for the next one
- The Kirtan splitter says what it found instead of `Done` (decided 2026-11-23, all shown green): `Splitter: Class` (no kirtan before the class, nothing to split), `Splitter: Kirtan` (singing throughout, a kirtan recording), `Splitter: Done` (cut into kirtan and class), and `Splitter: Not split` (a reviewer chose *Do not split* on a recording that it wanted to split)
- `<Tool> Review`: needs a person's judgement
- `<Tool> Failed`: an error such as a network problem, Baserow being down or an ffmpeg failure; can be retried
- `Skipped`: the step does not apply, for example splitting a kirtan-only recording
- `Excluded`: the reviewer stopped all processing of this file. The original stays where it was imported (never renamed or moved). If the Renamer already made a copy, Exclude moves that copy in processed-files to the OS Trash, after a warning (decided 2026-11-19)
- `Deleted`: the reviewer deleted the file (decided 2026-11-19): its copy in processed-files went to the OS Trash. The original and the Baserow row are untouched
- `Corrupted`: the media cannot be read
- `Processing complete`

## 9. Testing and development safety
- **Framework:** pytest.
- **Golden fixtures:** a YAML file lists each sample file with its expected name, split/trim timestamps (±1.5 s) and verse.
- **Test speed:** fast unit tests cover parsing and naming. Integration tests marked `slow` run real transcription on `trimming-samples/`.
- **Dev safety:** development runs use only `sample-files/`, and every tool and helper that changes files has a dry-run mode.

## 10. Confidence and learning
Thresholds are learned from labeled examples, not hard-coded. The goal is a balance: automate what the tools reliably get right and flag only what is genuinely uncertain.

### Labeled examples
- **Seed set:** the documented examples in the tool specs (the kirtan-splitter and class-trimmer timestamps, and the renamer and class-discoverer names) are stored in the golden fixtures.
- **Growing set:** every review outcome becomes a new labeled example. Approved unchanged confirms the tool, edited records the correction, and rejected marks a failure. Each is stored in the local DB with the tool's original proposal and its features.

### Confidence scores
- Each tool combines its evidence into one score per decision: a boundary for the splitter or trimmer, or a W for the renamer.
  - Splitter and trimmer evidence: common-phrase anchors, music/speech classifier margin, silence gap at the boundary, speaker-change evidence, and agreement between sources.
- Scores are calibrated against the labeled examples, so a score of 0.9 means about 90% of past decisions at that score were correct.

### Auto/review thresholds
- **Per tool:** each tool's threshold is the lowest score at which auto-applied decisions on the labeled set still reach the target precision. The default target is 95% of auto-applied cuts within ±1.5 s of the approved timestamp.
- **Below threshold:** the file is flagged for review.
- **Too few examples:** while a tool has fewer than 20 labeled examples, everything below a conservative starting threshold (0.9) goes to review. The Kirtan-splitter is the exception: it decides by the rule in its own section (sure or review), because five accurate trimming examples are all there is (2026-11-03).
- **Recalibration:** thresholds are recalculated automatically every 25 new review outcomes, and on demand with `mam calibrate`.
- **Spot checks:** a small share of auto-applied files (default 5%) is sent to review anyway, so the precision estimate stays honest.
- **Dashboard:** the media manager shows, per tool, the auto rate, the review rate and the measured precision. The target precision and spot-check rate are configurable in `.env`.

### Naming mismatches
The kirtan-splitter examples (`oslo-noi`, a kept `-2` index, `ZOOM0004` as a WHAT) show that real names are messy. The tools handle them with validation instead of fixed rules:
- **Validation:** each segment is checked against known values: ISO country codes, `travel_schedule` places, Baserow categories and verse patterns.
- **Auto-correct:** when exactly one valid correction exists, the tool applies it and records it in `notes`, for example `noi` → `no` (Norway, Oslo is in the travel schedule).
- **Review:** when no correction exists or several do, the file is flagged.
- **Meaningless parts dropped:** source indexes (`-2`) and device names (`ZOOM0004`, `R09_0003`) are removed from the new name, which follows the omit-unknown rule. The original name is always kept in the local DB and Baserow.
- **Learning:** corrections that reviewers make repeatedly (the same wrong token fixed the same way at least 3 times) are added as alias rules, so the same mistake is auto-corrected next time.

### KKS voice profile
- **Built from samples:** made from main-speaker segments of any file in `sample-files/` or `trimming-samples/`. The main speaker is the dominant speaker cluster in a class, confirmed by the class sections in the transcript.
- **Stored locally:** the profile is saved in the local DB.
- **Refreshed:** it is rebuilt when new approved recordings add coverage, such as other years or other microphones.
